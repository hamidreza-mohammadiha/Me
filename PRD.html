Business Model + PRD Summary

From seat-map toy to calibrated digital twin of the booking curve

How the Dynamic-vs-Static pricing simulation — same interface, same seat grid, same PnL% chart — graduates from a teaching sandbox into a decision-support instrument once its four hard-coded constants are replaced with live enterprise signals.

01 — Overview

One engine, two audiences

The simulation already separates mechanism (a pace-based repricing rule competing against a fixed reference price, arbitrated by a four-way customer utility function) from inputs (four constants: unit cost, a hand-built willingness-to-pay distribution, a Poisson arrival rate, and a static markup). That separation is the whole opportunity: swap the four constants for four live data feeds and the exact same interface — same seat grid, same commentator log, same PnL% chart — stops being a game and starts being a digital twin of the airline's actual booking curve.

A digital twin, in this sense, is a live, parameterized mirror of a real revenue-management process that can be run faster than real time, replayed against historical demand, or forked into "what-if" branches — without touching the production pricing engine. The same twin serves two audiences from one codebase: a pedagogical mode for analysts learning how pace-based repricing behaves, and a decision-support mode for pricing leadership evaluating a coefficient or policy change before it goes live.

02 — Twin Thesis

What makes it a twin and not just a sandbox

A sandbox uses invented numbers to teach a concept. A twin uses estimated or ingested numbers from the real system so that the simulated outcome is a genuine forecast, not just an illustration. Three properties separate the two:

  • Calibration, not authorship. Every constant in the current file (BASE_COST, the catchVal/lose distributions, lambda, STATIC_MARKUP) is presently chosen by whoever wrote the code. In the twin, each one is fit or pulled from a system of record on a schedule, and the simulation owns none of them.
  • Replayability against ground truth. Because the mechanism is unchanged, a calibrated run can be replayed against a historical booking day and its simulated seat-sell curve compared to what actually happened — giving a concrete calibration-error metric, not just face validity.
  • Decision consequence. In sandbox mode, moving the coefficient slider only changes a game score. In twin mode, the same slider represents a real policy lever whose simulated PnL% outcome is what a human uses to decide whether to change the live pricing rule.
Design constraint: the interface must not change shape between modes. The value of the twin is that the mental model an analyst builds in training mode (seat map, pace ratio, PnL%) transfers directly to reading a live decision-support run — a different skin would break that transfer.
03 — Dual Value Track

Pedagogical and decision-support are the same product, different inputs

Track A

Pedagogical

Hand-authored or lightly-randomized hyperparameters, safe to break. New RM analysts run scenarios (raise the coefficient too far, watch spillover balloon; set it too low, watch static win) to build intuition for the pace-ratio mechanism before they're allowed near a live pricing rule. No ERP or competitor feed required — this mode should work fully offline.

Track B

Decision Support

All four hyperparameters ingested from live systems for a specific route/date/cabin. Pricing leadership runs the current policy and a proposed policy side-by-side, reads the PnL% delta and the spillover count, and uses that comparison as evidence before changing the production repricing rule — the simulation becomes a pre-flight check, not a game.

Both tracks read from the same calibration pipeline (Section 06); Track A is simply pointed at a synthetic or historical snapshot instead of a live one, and has its safety rails relaxed since nothing downstream depends on the outcome.

04 — Packaging & Business Model

How this earns its keep

Internal capability

Training cost-out

Replaces shadowing/tribal-knowledge onboarding for RM analysts with a self-serve sandbox; measurable in reduced time-to-competency and fewer live-policy mistakes made by new hires.

Internal capability

Governed decision support

Gives pricing leadership a documented, replayable rationale ("the twin showed +X% PnL, -Y spillover") for every repricing-rule change — an audit trail that a bare coefficient tweak in production doesn't provide.

External offering

Consulting enablement asset

The same artifact doubles as a sales/enablement demo for a pricing-excellence engagement: a prospective client's own cost and competitor data can be dropped in live, turning a generic pitch into a client-specific forecast in the meeting.

Game-theory note: the twin models a single focal policy (the "dynamic airline") against a fixed reference strategy (the "static airline," standing in for −i, the rest of the market). It is a best-response evaluation, not a full equilibrium solver — competitors are not modeled as reacting to the focal airline's price. That is a deliberate scope boundary, called out again in Section 12.
06 — Data Architecture

From systems of record to the twin's clock

Both tracks call the identical twin engine. Track A can point the calibration layer at a synthetic or frozen historical snapshot; Track B always points at the freshest calibrated values.

07 — Goals & Non-Goals

Scope for this PRD

Goals

  • G1. Replace all four hard-coded constants with values sourced from a defined calibration pipeline, without changing the simulation's mechanism or interface.
  • G2. Support two run modes (sandbox / decision-support) from one codebase, switchable by which calibration snapshot is loaded.
  • G3. Make every twin run's inputs and outputs auditable — which calibration snapshot, which policy coefficient, what PnL%/spillover result — so a decision-support run can be cited as evidence for a live policy change.
  • G4. Preserve offline pedagogical use with no dependency on live ERP/competitor feeds.

Non-Goals (this phase)

  • NG1. The twin does not write back to the production pricing engine — it is advisory only in this phase.
  • NG2. Competitors are not modeled as strategic responders (no equilibrium solve); the static/−i price is treated as exogenous.
  • NG3. No multi-route or fleet-level optimization — the twin runs one route/date/cabin at a time.
08 — Personas

Who touches this and why

Track A

New RM Analyst

Needs to build intuition for pace-based repricing before being trusted near live rules. Runs many fast, low-stakes scenarios; cares about clarity of the commentator log more than data fidelity.

Track B

Senior Pricing Manager

Needs evidence before changing a live repricing coefficient. Runs a small number of high-fidelity, calibrated comparisons; cares about PnL% delta, spillover, and an auditable record of the run.

Owner

Data Science / RM Analytics

Owns the calibration pipeline — WTP model retrains, forecast integration, competitor feed hygiene. Cares about calibration error against replayed historical days, not the UI.

Non-functional

  • Latency: a full 40-second simulated run should render in under 5 seconds of wall-clock compute for decision-support use in a live meeting.
  • Access control: ERP cost data and competitor price feeds are commercially sensitive — decision-support mode requires role-gated access; sandbox mode does not.
  • Data freshness: decision-support runs must display the calibration snapshot's timestamp so users know how current the inputs are.
  • Portability: the interface remains a single self-contained artifact (no server dependency for rendering) so it can be shared as a file, consistent with its current form.

12 — Risks, Assumptions & Open Questions

What could go wrong, and what we haven't decided

Risks

  • Elasticity drift. The WTP model is fit on historical data and can go stale as market conditions shift; needs a monitored retrain cadence, not a one-time fit.
  • Static competitor assumption. Modeling the market reference price as exogenous (non-reactive) understates real competitor response to a visible pricing-policy change — a known simplification carried over from the original sandbox (see the −i note in Section 05).
  • Data sensitivity. Cost and competitor-price data are commercially sensitive; a leaked snapshot or an under-gated sandbox mode is a real exposure risk.

Assumptions

  • The existing repricing mechanism and utility model are directionally sound and do not need to change for this phase — only their inputs do.
  • RM analysts and pricing managers are willing to use a single tool for both training and evidence-gathering, rather than separate systems.

Open questions

  • Who owns the WTP model's retrain cadence — RM analytics or a central data-science function?
  • Should Track A ever be allowed to load a real (rather than synthetic) snapshot for realism, given the access-control risk that implies?
  • What is the minimum calibration error (Section 06, FR-6) required before a decision-support run is considered trustworthy enough to cite in a policy change?
